# 文档版本与资料冲突处理

上传时可填写所属手册、版本标记、生效日期、适用范围和有效状态。已有文档通过左侧“版本”按钮修改信息，无需重新计算向量；“原文”按钮可查看已归档或被新版替代的文件片段。

## 版本规则

| 字段 | 用途 |
| --- | --- |
| 所属手册 document_key | 明确哪些文件是同一份手册的不同版本，名称必须相同 |
| 版本标记 version | 展示用，如 2025版；不比较字符串大小 |
| 生效日期 effective_from | YYYY-MM-DD；按服务器当前日期判断是否生效 |
| 适用范围 scope | 精确匹配，如北京分公司；留空表示未标注，不代表通用 |
| 有效状态 status | active 可参与日期判断；archived 始终不进入检索 |

填写版本、生效日期或适用范围时，必须同时填写所属手册。系统不从文件名或正文中自动提取元信息，也不把上传时间作为版本依据。

检索先排除已归档和尚未生效的文件，再在**同一所属手册、同一适用范围**中选取已生效的最新日期。旧文件保留，不会自动删除或归档。若新版被归档而旧版仍有效，旧版会重新参与检索；整份手册停用时，应将其各版本都归档。

以下情况无法确定唯一适用文件：

- 相同手册、相同范围有多个相同最新日期的有效文件。
- 同组还有未标注日期的有效文件，不能假定它早于已标日期的文件。
- 同一手册有多个范围，但问题未选择范围；不从问题中的城市名自动推断。

最终检索结果涉及这类手册时，问答接口返回 `answer_mode=document_conflict`，列出无法排除的候选文件，并暂停大模型生成。即使 `top_k=1`，其他候选仍在独立的 `conflicts` 字段中，正常 `sources` 遵守 Top-K 上限。候选有匹配片段时展示摘录，没有匹配片段时明确显示未召回。

选择所属手册与范围，或核实后修正日期、归档失效版，可以消除歧义。范围为精确筛选：`scope="北京分公司"` 不回退到空范围；`scope=""` 只查未标注范围；省略或 null 表示不筛选。

## 网页演示

`examples/versions/` 提供三个虚构文件。展开“本次上传的版本信息”，填写下表，再选择对应文件上传。每次上传前确认字段对应当前文件。

| 文件 | 所属手册 | 版本 | 生效日期 | 范围 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 员工手册_旧版.md | 员工手册 | 2024版 | 2024-01-01 | 北京分公司 | 有效 |
| 员工手册_新版.md | 员工手册 | 2025版 | 2025-01-01 | 北京分公司 | 有效 |
| 员工手册_待核实版.md | 员工手册 | 待核实版 | 2025-01-01 | 北京分公司 | 有效 |

1. 上传旧版和新版，问题框上方选择“员工手册”“北京分公司”，用 BM25 问“北京出差住宿报销上限是多少？”。只应检索新版的 600 元规定；若调用模型，按现有 API 配置计费。
2. 上传待核实版，同日生效但写有 700 元规定。再次提问会显示“需要核实资料”，列出两份候选，**不调用模型**。
3. 将待核实版改成“已归档”，再次查询只检索新版。旧版可用“原文”查看，无需恢复参与检索。

文件正文也有填写说明，但不会自动变成元信息。演示时选定所属手册，避免混入未标注版本的原始演示员工手册。

## API 与验证

- `POST /api/documents`：multipart 表单支持五个元信息字段及 file。
- `PATCH /api/documents/{document_id}`：部分修改元信息；日期用 null 清空，文本用空字符串清空。修改对后续请求立即生效。
- `GET /api/documents`：元信息和 retrieval_state，包括 selected、superseded、future、archived、ambiguous。
- `GET /api/documents/{document_id}`：读取文件信息和解析后的片段，不返回向量。
- `POST /api/search`、`POST /api/chat`：增加可选 document_key、scope；结果增加 filters、conflicts、warnings，来源携带版本信息。

```json
{
  "question": "北京出差住宿报销上限是多少？",
  "mode": "bm25",
  "top_k": 3,
  "document_key": "员工手册",
  "scope": "北京分公司"
}
```

Python 的 `RagService.search` 仍返回来源列表，来源的 version_ambiguous 标识歧义；需要完整候选与提示时使用 `retrieve`。生成上下文包含文件版本和范围；遇到元信息歧义，answer 在本地返回，usage 为 null。

## 边界

当前依据**显式元信息**处理候选版本，没有自动证明两段自然语言互相矛盾。即使条款兼容，只要有效版本无法唯一确定，也会保守暂停生成。

未标所属手册的旧文件保持独立文档行为，应先补充元信息。不同手册之间或同一文件内部的矛盾，目前只通过提示词要求模型说明并引用双方，没有可靠的自动语义检测。[回答专项评测](public-answer-evaluation.md) 已验证两个虚构正文冲突场景及一个本地版本拦截场景；少量样本通过不能保证任意冲突都能被识别。

目前以**一份完整文件作为一个版本**，没有多文件共同组成一版的模型。拆分章节应分别使用稳定的所属手册标识，否则同日的不同章节会视为并列候选。失效截止日期、按历史日期问答和条款级覆盖尚未实现。

旧库启动时自动加列，已有文件默认 active、所属手册与版本为空，保留文字、向量和去重规则。相同内容仍全局去重；重复上传携带不同元信息会报错并要求编辑原文件，不会覆盖。原有评测留档代表当时的代码，不是本次新功能的质量保证。
